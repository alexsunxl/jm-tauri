# 连读模式设计

## 目标

连读不是在章节末尾简单跳转路由，而是把下一段内容追加到当前阅读流中：

- 多话作品：按章节顺序追加剩余章节。
- 单话作品：按用户选定的分类解析下一本，再追加该作品的唯一章节。
- URL、阅读进度、离线缓存和本地收藏始终使用作品根 ID，不使用当前章节 ID。

## ID 模型

| 字段 | 含义 | 用途 |
| --- | --- | --- |
| `requestedAid` | 用户进入详情时使用的 ID | 返回原详情入口、兼容旧链接 |
| `workId` | 规范化作品根 ID | 进度、收藏、缓存目录、阅读 URL |
| `albumId` | 详情接口返回的 album ID | 诊断和兼容接口差异 |
| `seriesId` | 接口返回的系列 ID | 多话作品根 ID 的优先来源 |
| `chapterId` | 当前章节 ID | 章节接口、图片路径、章节切换 |

`ReadingWork` 是可序列化的作品上下文。后续连读队列应引用它，不应再次从当前章节反推作品 ID。

## 推荐队列

阅读队列由多个 segment 组成，每个 segment 至少包含：

```ts
type ReadingSegment = {
  work: ReadingWork;
  chapterId: string;
  chapterTitle: string;
  status: "idle" | "loading" | "ready" | "error";
};
```

多话作品先把当前章节之后的章节转换为 segment。单话作品到达末尾时，由分类解析器返回下一本 `ReadingWork`，再加入它的单个章节。

不要把不同作品的图片直接拼成一个无边界数组。每个 segment 必须独立持有加载、取消、错误重试、分页和进度状态，否则切换作品时无法正确释放 object URL 和请求任务。

## 单话分类解析

分类解析器的输入应是显式的分类 ID 或分类 slug，不能直接取任意标签：

1. 用户首次开启单话连读时选择分类，或使用详情来源已有的明确分类。
2. 通过分类/搜索接口按稳定顺序分页获取候选作品。
3. 排除当前 `workId`、本次会话已读作品和无有效章节的结果。
4. 将候选详情规范化为 `ReadingWork` 后加入队列。
5. 保存分类键、分页游标和已读 work ID；恢复阅读时继续同一序列。

随机推荐可以作为策略，但队列一旦生成就必须固定，避免返回阅读页后“下一本”变化。

## 加载和回收

- 当前 segment 剩余约 2-3 页时预取下一个 segment 的章节元数据。
- 当前 segment 最后一页进入可视区时开始加载下一段首屏图片。
- DOM 只保留上一段、当前段和下一段；更早图片保留尺寸占位并释放 blob URL。
- 活跃 segment 变化时使用 `replace` 更新 URL，避免每一页或每一段污染浏览器历史。
- 进度写入活跃 segment 的 `workId + chapterId + pageIndex`。
- 下一段加载失败时保留明确的重试按钮，不自动跳过作品。

## 当前实现

多话连续阅读已经以可配置功能落地，默认关闭，可在设置页或阅读菜单中切换：

- 初次进入时渲染当前章节和下一章节，下一章节以低并发预加载。
- 活跃章节变化后，DOM 窗口保持上一章、当前章、下一章，最多三个 segment。
- 窗口向前或向后移动时，以当前 segment 的视口位置做滚动补偿，避免增删章节导致跳动。
- 每个 segment 独立维护请求取消键、图片调度、重试、object URL 和阅读进度。
- 桌面方向键在关闭连续阅读时切换路由；开启后滚动到相邻 segment，操作均显示 toast。

当前 URL 仍表示进入阅读页时的章节，滚动跨章不会写入浏览器历史。恢复位置以作品根 ID、活跃章节 ID 和页码为准。

## 实施阶段

1. 已完成：统一 `ReadingWork`、规范 ID、进度迁移和返回上下文。
2. 已完成：抽取独立 `ReadingChapterSegment`，实现多话三段滑动窗口。
3. 下一步：增加分类选择和单话下一本解析器。
4. 后续：增加跨作品队列持久化、可调预加载阈值及离线策略。

多话连读先落地，可以验证 segment 生命周期和进度切换；单话跨作品只是在同一队列上增加一个异步 resolver，不需要再改阅读页核心结构。
